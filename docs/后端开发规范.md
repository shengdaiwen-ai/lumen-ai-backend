## 0. 红线清单（动手前先读这 19 条）

违反下面任意一条，代码一律不合并。

> 19 条编号红线 + 2 条字母补充（1b 基础设施地址、8b 建表排序规则），共 21 条禁止项。

| # | 红线 | 为什么 |
|---|---|---|
| 1 | **源码中禁止出现任何明文凭据** | 本仓库是**公开仓库**。真实值只能放 `application-local.yml`（已 gitignore）或环境变量 |
| 1b | **禁止在代码、注释、文档里写真实基础设施地址**（生产 IP、域名、库名、账号） | 同为公开仓库。示例一律用 `<DB_HOST>` / `example.com` 这类占位符 |
| 2 | **禁止新增 Mapper XML** | 全项目零 XML，一律用 MyBatis-Plus 的 `LambdaQueryWrapper`。混用会破坏一致性 |
| 3 | **禁止在 `@RestController` 里写业务逻辑** | 控制器只做参数接收 + 调 Service + 包 `R<T>`。业务在 Service |
| 4 | **禁止绕过 `R<T>` 直接返回裸对象** | 前端 `request<T>()` 依赖 `{code,message,data}` 结构解包 |
| 5 | **禁止抛裸 `RuntimeException`** | 统一抛 `BusinessException`，由 `GlobalExceptionHandler` 兜底 |
| 6 | **禁止对 `getupdates` 发起任何额外请求** | iLink 长轮询游标由 Electron 主进程独占，服务端再发一次会**抢走消息**导致桌面端漏收。这是本项目最严重的历史事故 |
| 7 | **禁止在接口里做同步网络探测** | 曾因"绑定状态探测"用 8 秒超时读长轮询，导致每次进办公助理卡 8 秒。接口响应目标 < 500ms |
| 8 | **数据库变更必须走幂等迁移，且脚本必须以 UTF-8 执行** | 用 `DbMigrationRunner` 或 `db/migration_*.sql`，先查 `information_schema` 再执行；脚本执行一律走 `DbMigrationRunner#runScript()`（内部用 `EncodedResource` 显式指定 UTF-8），**禁止**直接调单参 `ScriptUtils.executeSqlScript(conn, resource)` |
| 8b | **建表必须显式写 `COLLATE=utf8mb4_unicode_ci`** | 只写 `DEFAULT CHARSET=utf8mb4` 时，表排序规则取的是**该字符集的默认值**（MySQL 8 = `utf8mb4_0900_ai_ci`），**不是**库默认值 |
| 9 | **禁止对生产库执行 `schema.sql`** | 该文件含 `DROP TABLE IF EXISTS`，只用于本地初始化 |
| 10 | **新增受保护接口必须登记到 `AUTH_PATTERNS`** | `JwtAuthFilter` 用白名单式匹配，漏登记 = 接口裸奔 |
| 11 | **禁止 `@ConfigurationProperties` 与 `@Value` 混用同一前缀** | 自定义配置统一收敛到 `LumenProperties` |
| 12 | **日志禁止打印凭据、完整请求体、token** | 日志会落盘 30 天且体积上限 3GB |
| 13 | **接口必须幂等或明确标注非幂等** | 定时任务、重试、SSE 重连都会重复触发 |
| 14 | **禁止把可运营的业务数据硬编码在代码里**（套餐、价格、权益、折扣、上下架状态、活动配置…） | 这类数据属于运营面，必须建表 + 幂等迁移 + 查库返回。写死在 Service 常量里意味着每次改价、调权益都要改代码重新发版，运营侧完全无法自助 |
| 15 | **禁止把带纳秒的时间写入秒级 `DATETIME` 列后立刻拿它做「到点 / 已过期」判断** | MySQL 降精度是**四舍五入**而不是截断：`12:20:30.800` 存进去变成 `12:20:31`，比真实时刻**晚**最多 1 秒。2026-09-18 实例：`subscription_credit_grants.period_start` 带纳秒落库后被写大 1 秒，紧接着的惰性发放拿 `LocalDateTime.now()` 去比就判「还没到点」→ 新购/升级的当期积分**静默不发**，约 50% 命中（用户侧表现＝「买了套餐积分没到账」，且不报任何错）。凡写库的值参与「到点」判断，一律先 `withNano(0)` |
| 16 | **读取 Spring AI 的元数据必须用类型化 accessor**（`chunk.getMetadata().getUsage()` / `getModel()`），**禁止**按 metadata Map 的 key 去取 `"usage"` / `"model"` | Spring AI 2.0 把 `usage` 放在 `ChatResponseMetadata` 的**字段**上，`entrySet()` 里只有 `keyValue()` 写进去的附加键（`finishReason` / `role` 之类）。2026-09-18 实例：按 Map 取 `usage` 永远取到空 → `meta.inputTokens` 恒为 0 → 整条链路静默退化成 `chars/4` 估算（流水标题张张带 `[估算]` 前缀，实际 token 被低估 7 倍），而且**不报任何错**。同一轮里 usage 只在最后一个 chunk 出现且是整轮累计值，取法要「末次为准」，逐 chunk 累加会重复计数 |
| 17 | **禁止把计费口径、状态标记、来源标记写进业务文本列**（如往 `record_title` 里拼 `[估算] ` 前缀），一律用独立字段承载 | 文本列是给人看的，机器可读的口径必须结构化：2026-09-18 实例：估算标记写进标题后，用量明细里每一行都带 `[估算]`，用户以为记录坏了；而且前端要靠 `startsWith('[估算] ')` 才能判断，一旦标题超长截断或用户自己输入同样前缀就误判。正确做法是 `credit_transactions.estimated` 这样的独立列 |
| 18 | **本机绝对路径不得进入服务端**（表列、DTO/VO、日志、错误信息、SSE 载荷都不许出现） | 产品部署在云服务器上，本机路径对服务端既**无法校验有效性**（同形路径会静默读写服务器上无关目录），又是**隐私泄露**（路径含用户名与目录结构）。2026-09-21 实例：工作空间功能若沿用既有的 `sessions.project_path` 裸路径列设计，服务端就会变成"存用户目录清单的数据库"。正确做法是服务端只存 `workspace_id` 等**不透明引用**，绝对路径只在客户端本地（`ai-coding-settings.workspacePaths`），路径解析与沙箱判定也一律在客户端完成 |
| 19 | **客户端显式指定的引用拿不到时必须显式失败，禁止"静默降级"**（选了工作空间却绑不上 → 404，而不是"按无空间创建"） | 静默降级让「用户以为生效了」与「系统以为处理完了」同时成立，故障表现是「功能莫名其妙不工作」而**不报任何错**，排查成本极高（要靠翻日志 + 比对缓存才能定位）。2026-09-21 实例：`SessionService#create` 对跨设备/已移除的 `workspaceId` 一律 `log.info` 后**按无空间会话创建** —— 前端选中的空间在服务端早已被移除（客户端 `workspaceStore` 只缓存不重拉），用户因此得到一个"看着绑了、其实没绑"的会话，**前端零提示、后端零异常**。正确做法：`resolveForDevice` 返回 null 即抛 `404 WORKSPACE_NOT_FOUND`；**只有请求本身没带 `workspaceId`** 时才建无空间会话。同一条原则也适用于"字段解析失败就静默取默认值"这类写法 |

### 分层职责（严格单向依赖）

```
Controller  →  Service  →  Mapper  →  DB
     ↓            ↓
    DTO          Entity
```

| 层 | 允许做 | 禁止做 |
|---|---|---|
| `Controller` | 取 `UserContext`、参数校验注解、调 Service、包 `R.ok()` | 写业务判断、直接用 Mapper（极少数只读例外）、try/catch 业务异常 |
| `Service` | 业务逻辑、事务、抛 `BusinessException`、调用其他 Service | 感知 `HttpServletRequest`、返回 `R<T>`、返回 `ResponseEntity` |
| `Mapper` | 继承 `BaseMapper<T>`，复杂查询用 `LambdaQueryWrapper` | 写业务逻辑 |
| `entity` | 与表结构一一对应，MyBatis-Plus 注解 | 加业务方法、加 `@JsonIgnore` 之外的展示逻辑 |
| `dto` | 请求/响应载体，`@Data` + 校验注解 | 直接被持久化（除非本来就是实体） |

**⚠️ 现有空包**：`browser/`、`common/utils/`、`mcp/`、`plugin/`、`schedule/`、`vo/` 目前**零文件**。新增代码请优先放进已有实际使用的包，不要往空包里塞；若无用应删除。

**⚠️ 孤儿代码**：`config/OpenClawProperties.java`、`service/OpenClawGatewayService.java`、`application.yml` 里的 `openclaw.gateway-url` 已无调用方（链路已迁 iLink Bot），待清理。

## 3. 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 包 | 全小写，单词不缩略 | `com.lumenai.backend.workassistant` |
| 类 | PascalCase | `SessionService`、`JwtAuthFilter` |
| 接口 | 不加 `I` 前缀 | `Tool`（不是 `ITool`） |
| 接口实现 | 语义化命名，不用 `Impl` 后缀 | `DateTimeTool`（不是 `DateTimeToolImpl`） |
| 方法 | camelCase，动词开头 | `listByUser`、`getOrThrow`、`verifyBindingLocally` |
| 常量 | `UPPER_SNAKE_CASE` | `AUTH_PATTERNS`、`DEFAULT_TZ` |
| 数据库表 | 蛇形复数 | `users`、`sessions`、`channel_accounts` |
| 数据库字段 | snake_case | `workspace_id`、`permission_mode` |
| 配置项 | kebab-case | `max-loop-rounds` |
| DTO | 动词/名词 + `Request` / `Response` | `SessionCreateRequest`、`ScheduleResponse` |

**Controller 方法名 = 动作**：`list` / `create` / `get` / `update` / `delete` / `refresh`。
**Service 查询方法返回值策略**：`getById` 找不到抛异常；`findByXxx` 返回 `null` 或 `Optional`。命名必须让调用方一眼看出会不会抛。

## 4. 接口层（Controller）规范

### 4.1 标准结构

```java
@Tag(name = "会话管理", description = "会话 CRUD 与消息历史")
@RestController
@RequestMapping("/sessions")
@RequiredArgsConstructor
public class SessionController {

    private final SessionService sessionService;

    @Operation(summary = "列出当前用户的会话")
    @GetMapping
    public R<List<SessionResponse>> list() {
        return R.ok(sessionService.listByUser(UserContext.get()));
    }

    @Operation(summary = "创建会话")
    @PostMapping
    public R<SessionResponse> create(@RequestBody(required = false) SessionCreateRequest req) {
        if (req == null) req = new SessionCreateRequest();
        return R.ok(SessionResponse.from(sessionService.create(UserContext.get(), req)));
    }
}
```

要点：

- 类上必须同时有 `@Tag`，方法上必须有 `@Operation(summary=...)` —— Swagger 文档是给别人看的。
- 注入统一用 `@RequiredArgsConstructor` + `private final`（构造器注入），**禁止 `@Autowired` 字段注入**。
- **`context-path = /api` 已在 `application.yml` 配好**，`@RequestMapping` 里**不要**再写 `/api` 前缀。
- 用 `@PatchMapping` 做局部更新，`@PutMapping` 做整体替换。
- 路径参数用 `@PathVariable`，查询参数用 `@RequestParam`，请求体用 `@RequestBody`。

### 4.2 当前用户 ID 的获取

```java
Long userId = UserContext.get();   // ThreadLocal，由 JwtAuthFilter 注入
```

**禁止**从请求体/查询参数里读 `userId` 做鉴权（可被伪造）。`UserContext` 在请求结束时由 filter 清理。

### 4.3 资源归属校验

所有按 ID 操作的接口**必须**校验资源属于当前用户：

```java
// ✅ Service 里校验
public Session getOrThrow(Long userId, Long id) {
    Session s = sessionMapper.selectById(id);
    if (s == null || !s.getUserId().equals(userId)) {
        throw new BusinessException(404, "会话不存在");
    }
    return s;
}
```

**禁止**只按 ID 查询就返回（越权漏洞）。

### 4.4 无 JWT 的内部接口

Electron 主进程直调的接口（`/work-assistant/accounts/confirm`、`/messages/inbound`、`/accounts/session-expired`）走 `noAuth=true` + `ilinkUserId` 反查用户。这类接口：

- **必须**登记在 `JwtAuthFilter.SKIP_PATHS`。
- **必须**在方法注释里写明"为什么可以无认证"以及反查逻辑。
- **禁止**用它们做任何写操作之外的高权限行为。

## 5. 统一响应与异常

### 5.1 `R<T>` 是唯一出口

```java
R.ok()                    // code=200, data=null
R.ok(data)                // code=200
R.fail(400, "参数错误")    // 业务错误
R.fail("服务异常")         // 默认 code=500
```

结构：`{ code, message, data, timestamp }`。**`code == 200` 才代表成功**，前端据此判定。

- **禁止**直接 `return new R<>()` 手搓。
- **禁止**成功时返回 `R.fail` 之外的错误码。
- 需要非 200 的成功语义时（如 201），先团队讨论 —— 当前约定是统一 200。

### 5.2 异常处理

```java
// ✅ 业务异常（会被 GlobalExceptionHandler 转成 R.fail(code, msg)）
throw new BusinessException("邮箱已注册");              // code=400
throw new BusinessException(404, "会话不存在");
throw new BusinessException(401, "Refresh Token 无效或已过期");

// ❌ 禁止
throw new RuntimeException("...");
return R.fail(500, e.getMessage());   // 在 Controller 里手动 catch
```

`GlobalExceptionHandler` 已覆盖：

| 异常 | 返回 |
|---|---|
| `BusinessException` | `R.fail(ex.getCode(), ex.getMessage())`，打 `warn` |
| `MethodArgumentNotValidException` / `BindException` | `R.fail(400, "字段: 消息; ...")` |
| `NoResourceFoundException` | `R.fail(404, "Resource not found: ...")` |
| `Exception` | `R.fail(500, "Internal server error: ...")`，打 `error` + 堆栈 |

**新增异常类型时，必须在 `GlobalExceptionHandler` 里加对应 handler**，否则会落到兜底的 500 分支。

**错误消息面向用户**：写中文、说人话（"邮箱已注册"），不要写技术细节（"Duplicate entry for key 'idx_email'"）。

## 6. 参数校验

用 Jakarta Validation，**在 DTO 上声明，不要在 Service 里手写 if**：

```java
@Data
public class RegisterRequest {
    @NotBlank(message = "邮箱不能为空")
    @Email(message = "邮箱格式不正确")
    private String email;

    @NotBlank(message = "密码不能为空")
    @Size(min = 6, max = 32, message = "密码长度需在 6~32 位之间")
    private String password;
}
```

Controller 上加 `@Valid`：

```java
public R<AuthResponse> register(@Valid @RequestBody RegisterRequest req) { ... }
```

规则：

- **`@NotBlank` 优先于 `@NotNull`**（能挡掉空串）。
- **message 必须是中文**，会原样返回给用户。
- 跨字段校验（如两次密码一致）放 Service，抛 `BusinessException`。
- 嵌套对象校验要加 `@Valid` 级联注解。

## 7. 认证与鉴权

### 7.1 架构

```
请求 → JwtAuthFilter（OncePerRequestFilter）
         ├─ 加 CORS 头 + 放行 OPTIONS
         ├─ path ∈ SKIP_PATHS     → 直接放行
         ├─ path ∉ AUTH_PATTERNS  → 直接放行（公开接口）
         └─ 需要鉴权 → 解析 Bearer Token
                        ├─ 有效 → UserContext.set(userId) → 放行
                        └─ 无效/缺失 → 返回 R.fail(401)
```

### 7.2 ⚠️ 新增受保护接口必须登记

`JwtAuthFilter` 是**白名单式**的，只有匹配 `AUTH_PATTERNS` 前缀的路径才校验 Token。**新增一个需要登录的接口路径时，必须同时把前缀加进 `AUTH_PATTERNS`**，否则接口会完全裸奔。

```java
private static final Set<String> AUTH_PATTERNS = Set.of(
        "/api/auth/me", "/api/sessions", "/api/chat", "/api/tools",
        "/api/schedules", "/api/schedule-runs", "/api/files", "/api/profile",
        "/api/subscription", "/api/credits", "/api/workspace",
        "/api/work-assistant/accounts", "/api/work-assistant/messages",
        "/api/work-assistant/sessions", "/api/work-assistant/reply/stream"
);
```

注意 `AUTH_PATTERNS` 用的是 `startsWith` 前缀匹配，所以路径设计要让前缀能覆盖整个资源：

- ✅ `/api/work-assistant/accounts`、`/api/work-assistant/accounts/{id}`
- ⚠️ 若新增 `/api/work-assistant/settings`，需追加 `/api/work-assistant/settings`

### 7.3 JWT 约定

`JwtUtil` 提供的方法：

| 方法 | 用途 |
|---|---|
| `generate(userId, email, username)` | 签发 Access Token |
| `generateRefresh(userId, email, username)` | 签发 Refresh Token |
| `validate(token)` | 校验签名与有效期 |
| `isRefreshToken(token)` | 区分 Access / Refresh |
| `parseUserId(token)` | 从 Token 取 userId |
| `extractToken(header)` | 从 `Authorization` 头剥离 `Bearer ` 前缀 |

- 有效期：Access 2 小时、Refresh 7 天。
- Header 固定 `Authorization: Bearer <token>`。
- **Token 里不放敏感信息**（密码、手机号等）。
- 密钥走 `${JWT_SECRET:...}`，生产必须用至少 32 字节随机串。

### 7.4 已知不一致（待修）

`JwtAuthFilter` 里硬编码了 `Access-Control-Allow-Origin: *`，而 `WebMvcConfig` 用的是 `lumen.cors.allowed-origins` 白名单 + `allowCredentials(true)`。浏览器规范下 `*` 与 credentials 不能共存，二者实际由 filter 的表头生效。**新增跨域需求时应统一到 `LumenProperties`，不要继续加硬编码。**

## 8. Service 层规范

### 8.1 类结构

```java
@Service
@RequiredArgsConstructor
public class SessionService {

    private final SessionMapper sessionMapper;
    private final MessageMapper messageMapper;

    public List<SessionResponse> listByUser(Long userId) { ... }
    public Session getOrThrow(Long userId, Long id) { ... }
}
```

- 用 `@RequiredArgsConstructor` + `private final` 构造器注入。
- 类和方法加中文 Javadoc，说明**业务语义**而非重复方法名。
- Service 返回**实体或 DTO**，**不返回** `R<T>`。
- 🔴 **列表接口不得用状态过滤把「非活跃」行藏掉**（2026-09-22 事故：用户归档后退出重登，归档记录凭空消失）。`listByUser` 曾写 `.eq(Session::getStatus, "active")`，结果 `pinned` / `archived` 的会话根本不下发 —— 前端侧栏要渲染置顶板块、设置页「数据管理」要渲染已归档任务，两者的数据源都是这份列表，被服务端过滤后它们彻底不可见，用户看成「数据丢了」。**分状态的展示职责归前端**（前端按 `status` 分组渲染），服务端只保证「返回该用户的全部非删除行」。同一教训在孤儿空间清理里也出现过（§空间生命周期：`含已归档 / 置顶`）。

### 8.2 ⚠️ 禁止同步网络探测

**任何接口路径上都不允许出现"探测式"的同步 HTTP 调用。** 历史事故：办公助理的绑定状态查询调用了 iLink 长轮询探测，token 有效时服务端挂住连接，导致每次进页面卡满 8 秒超时。

正确做法：

```java
// ✅ 只读库，零网络调用
public boolean verifyBindingLocally(String channel, Long userId) { ... }

// ❌ 探测式网络调用
public boolean verifyBinding(String channel) {
    return ilinkBotClient.probeSession(...);   // 可能挂 8 秒
}
```

判定标准：接口 P99 应 < 500ms。若某操作天然慢（LLM 生成、大文件），必须走 SSE 流式或异步任务，不能阻塞 HTTP 响应。

### 8.3 事务

- 写操作加 `@Transactional(rollbackFor = Exception.class)`。
- **禁止**在事务方法里做网络调用（LLM、HTTP），会长时间占着数据库连接。
- 事务方法**禁止**是 `private`（Spring AOP 代理不生效）。
- 自调用（同类内部方法互调）不走代理，事务会失效 —— 需要时抽到另一个 Bean。

### 8.4 幂等

定时任务、外部回调、SSE 重连都可能重复触发。写操作前必须判断是否已处理：

```java
ChannelMessage exist = messageMapper.selectOne(
        new LambdaQueryWrapper<ChannelMessage>()
                .eq(ChannelMessage::getIlinkMsgId, ilinkMsgId));
if (exist != null) return exist;   // 幂等返回
```

### 8.5 🔴 禁止静默降级（红线 19）

**客户端显式指定的引用拿不到时，必须显式失败，不得"降级成默认语义"悄悄办完。**

```java
// ✅ 显式失败：客户端明确要绑这个空间，绑不上就报错
Long workspaceId = req.getWorkspaceId();
if (workspaceId != null) {
    Workspace ws = workspaceService.resolveForDevice(userId, workspaceId, deviceId);
    if (ws == null) {
        throw new BusinessException(404, ErrorCode.WORKSPACE_NOT_FOUND,
                "所选工作空间不存在或不在当前设备，请重新选择工作空间");
    }
    s.setWorkspaceId(ws.getId());
}
// 只有请求本身没带 workspaceId，才是"用户就要无空间会话"

// ❌ 旧写法（2026-09-21 事故）：绑不上就 log 一句、当没绑继续建
//    → 用户「选了工作空间」却得到无空间会话，前后端全程零提示
```

**为什么**：降级路径上"用户以为生效了"与"系统以为处理完了"同时成立，故障表现为「功能莫名其妙不工作」而**不报任何错**，只能靠翻日志 + 比对客户端缓存定位。

**边界**：后台链路（`ScheduleRunner` 等）对已失效引用仍是**宽松处理**（记 WARN、按无空间跑、不标记失败），因为那里没有"用户此刻的显式选择"——见《工作空间选择-需求设计》FR-35。判断依据是**这个引用是不是用户当场选的**，不是"有没有传值"。

> 同类反模式：`Optional.orElse(默认值)` 吞掉解析失败、`try/catch` 后返回空列表、DTO 字段缺失就用兜底常量。要么显式失败，要么把降级**写进返回值**让调用方知道（如 `truncated=true`、`estimated=true` 这类标记位）。

## 9. 持久层规范（MyBatis-Plus）

### 9.1 实体

```java
@Data
@TableName("sessions")
public class Session {

    @TableId(type = IdType.AUTO)
    private Long id;

    /** 归属用户，所有查询必须带上 */
    @TableField("user_id")
    private Long userId;

    @TableField("workspace_id")
    private Long workspaceId;

    @TableField("created_at")
    private LocalDateTime createdAt;
    @TableField("updated_at")
    private LocalDateTime updatedAt;
}
```

- 全项目**零 Mapper XML**（`resources` 下没有 `mapper/*.xml`，`mapper-locations` 配置留着只是兜底）。
- 字段用 `@TableField` 显式映射，**不要依赖驼峰自动转换**（虽然 `map-underscore-to-camel-case: true` 已开，显式更安全）。
- 主键统一 `@TableId(type = IdType.AUTO)`，数据库 `BIGINT AUTO_INCREMENT`。
- 时间字段用 `LocalDateTime`，不用 `Date` / `Timestamp`。
- 类注释写清对应表名。
- 不使用 Lombok `@EqualsAndHashCode`/`@ToString` 于实体上（避免懒加载陷阱），`@Data` 足够。

### 9.2 查询

```java
// ✅ 参数化 + 类型安全
sessionMapper.selectList(new LambdaQueryWrapper<Session>()
        .eq(Session::getUserId, userId)
        .eq(Session::getStatus, "active")
        .orderByDesc(Session::getUpdatedAt));

// ❌ 字符串拼接、SQL 注入风险
sessionMapper.selectList(new QueryWrapper<Session>().apply("user_id = " + userId));
```

**铁律：所有按用户维度的查询必须带 `user_id` 条件**（防止越权）。

### 9.3 逻辑删除（⚠️ 配置已开，但当前实际未启用）

`application.yml` 里声明了全局逻辑删除：

```yaml
mybatis-plus.global-config.db-config:
  logic-delete-field: deleted
  logic-delete-value: 1
  logic-not-delete-value: 0
```

**但这是一项"空配置"**：核对确认，`schema.sql` / `db/*.sql` 中**没有任何表带 `deleted` 列**，`entity/` 下 10 个实体也**没有一个声明该字段**。也就是说当前的删除操作全是物理删除，上述配置没有生效。

因此：

- **现状**：`mapper.deleteById(id)` 是**真删**，删了就没了。做数据恢复相关功能时不要假设有软删除。
- **新增表时**：若业务需要软删除，必须**同时**做两件事 —— 表里加 `deleted TINYINT(1) NOT NULL DEFAULT 0`，实体里加 `@TableLogic private Integer deleted;`。只加表字段不生效，只加注解会报 Unknown column。
- **写查询时**：不要依赖框架自动过滤 `deleted`，当前所有查询都是全量。
- 建议择机统一决策：要么给所有表补齐软删除，要么把这段配置删掉避免误导。

### 9.4 分页（⚠️ 拦截器已注册，但当前零使用）

`MyBatisPlusConfig` 已注册 `PaginationInnerInterceptor(DbType.MYSQL)`，但**核对确认当前没有任何代码使用分页**（无 `selectPage` / `new Page<>` 调用）。列表接口目前都是 `selectList` 全量返回。

新增列表接口时的规则：

```java
Page<ScheduleRun> page = scheduleRunMapper.selectPage(
        new Page<>(pageNum, pageSize),
        new LambdaQueryWrapper<ScheduleRun>()
                .eq(ScheduleRun::getUserId, userId)
                .orderByDesc(ScheduleRun::getCreatedAt));
```

- **`pageSize` 必须有上限**（建议 ≤ 100），禁止让前端传任意大值。
- 数据量可能增长的列表接口**必须分页**，禁止无限制 `selectList`。
- 分页参数用 `pageNum` / `pageSize`，响应统一返回 `total` / `records`。

## 10. 数据库变更规范

### 10.1 两条路径

| 场景 | 做法 |
|---|---|
| 本地从零初始化 | 改 `resources/db/schema.sql`（⚠️ 含 `DROP TABLE`，**只能本地跑**） |
| 已有环境的增量变更 | 写 `resources/db/migration_*.sql`，并在 `DbMigrationRunner` 里注册 |

### 10.2 `DbMigrationRunner` 规范

启动时执行，**必须幂等**。标准范式：

```java
private void addColumnIfNotExists(String table, String column, String definition, String after) {
    try {
        Integer count = jdbcTemplate.queryForObject(
                "SELECT COUNT(*) FROM information_schema.COLUMNS " +
                        "WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = ? AND COLUMN_NAME = ?",
                Integer.class, table, column);
        if (count != null && count > 0) {
            log.debug("{}.{} 已存在，跳过迁移", table, column);
            return;
        }
        jdbcTemplate.execute("ALTER TABLE " + table + " ADD COLUMN " + column + " " + definition
                + (after != null ? " AFTER " + after : ""));
        log.info("迁移完成：{}.{} 字段已添加", table, column);
    } catch (Exception e) {
        log.warn("{}.{} 迁移失败（可能已存在）: {}", table, column, e.getMessage());
    }
}
```

规则：

- **先查 `information_schema` 再执行**，绝不无脑 `ALTER`。
- **失败只 `warn` 不中断启动**（迁移失败不应导致服务起不来）。
- 类上加 `@Order(1)` 保证在其他 `CommandLineRunner` 之前执行。
- 新增字段要**给默认值**（`NOT NULL DEFAULT x`）或允许 `NULL`，避免存量行报错。
- **大表加字段要评估锁表时间**，必要时用 `pt-online-schema-change`。

### 10.3 字段设计约定

- 字符集 `utf8mb4`，排序规则 `utf8mb4_unicode_ci`，**建表时两个都要显式写**：`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`。
  - ⚠️ **只写 `DEFAULT CHARSET=utf8mb4` 是不够的**：这种情况下表排序规则取的是「该字符集的默认值」——MySQL 8 是 `utf8mb4_0900_ai_ci`，**而不是**库默认的 `utf8mb4_unicode_ci`。
    于是同一张库里两种 ci 规则并存，跨表 JOIN 字符串列随时会撞上 `Illegal mix of collations (...unicode_ci,IMPLICIT) and (...0900_ai_ci,IMPLICIT)`，且这个错只在特定查询上偶发，极难定位。
    2026-09-18 实例：15 张由迁移脚本建的表全部落成 `utf8mb4_0900_ai_ci`，而 `schema.sql` 建的表是 `utf8mb4_unicode_ci`（因为后者紧跟在 `CREATE DATABASE ... DEFAULT COLLATE` 之后、且未写 CHARSET，才继承了库默认值）。
  - `DbMigrationRunner#ensureUtf8mb4Collation()` 每次启动兜底把不一致的表 `CONVERT TO` 统一过来（幂等：全一致时只查一次 `information_schema` 就返回，不做任何 DDL）。
    **但不要依赖它救场**——脚本自己写对，兜底只防漏网。
  - ⚠️ **脚本里的中文必须以 UTF-8 被读取**：`ScriptUtils.executeSqlScript(conn, resource)` 单参重载会退回 `Charset.defaultCharset()`（zh_CN 的 Windows + JDK 17 = GBK），
    脚本里的中文 `COMMENT` 与种子数据会被按 GBK 误读后写库，落成 `绉\ue21a垎` 这类乱码；**其中 U+FFFD 已经吃掉了原始字节，事后无法反解，只能逐条重写**。
    统一走 `DbMigrationRunner#runScript()`。
- 主键 `BIGINT AUTO_INCREMENT`。
- 时间 `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`，更新时间戳用 `ON UPDATE CURRENT_TIMESTAMP`。
  - ⚠️ **`DATETIME` 精度只到秒，且 MySQL 降精度是「四舍五入」不是截断**：`12:20:30.500` 存进去变 `12:20:31`（比真实时刻**晚**最多 1 秒）。
    所以凡是「写入后紧接着要拿它做 `<= NOW()` 判断」的列（典型：发放计划的 `period_start`），**写库前必须先 `withNano(0)`**。
    2026-09-18 实例：`subscription_credit_grants.period_start` 直接落纳秒 → 被写大 1 秒 → 紧随其后的惰性发放判定「还没到点」→
    新购/升级当期积分静默不发，约 50% 命中（用户侧＝「买了套餐积分没到账」，无任何报错）。只有「判断到点」这一侧需要截断；
    纯展示 / 向后顺延的时间不用管。
- 状态/枚举字段用 `VARCHAR(16~32)` 存字符串（不用魔法数字），并在 `COMMENT` 里列出全部取值。
- 建索引：外键、高频查询条件、排序字段。
- **金额一律 `DECIMAL(12,2)` + Java `BigDecimal`**（现状：`users.balance`、`subscription_plan_billings.price`、`credit_accounts.balance`）。禁止 `FLOAT`/`DOUBLE`（浮点误差），Java 侧禁止用 `Double` 接；出参直接透传 `BigDecimal`。金额列的 `COMMENT` 要写明用途（如 `账户余额（元），可用于购买套餐`）。
- **金额与积分的变动必须留痕 + 原子增减**：增减都要有流水/批次记录（只改余额不留痕无法对账）；**扣减**一律 `UPDATE ... SET x = x - ? WHERE id = ? AND x >= ?` 条件更新，禁止"先 SELECT 判断再 UPDATE"（并发下会扣穿）；**增加**同样用 `SET x = x + ?` 自增，禁止"先读出来加完再写回"（并发下会丢更新）。
  - 实现落在**四处**，都用 `@Update` 注解 + `#{}` 预编译、返回**影响行数**：`UserMapper#deductBalance`（0 行 = 余额不足）、`CreditAccountMapper#addBalance`（0 行 = 积分账户不存在）、`CreditRewardMapper#reclaim`（0 行 = 该批次剩余不足，调用方抛异常回滚整笔升级）、`CreditAccountMapper#deductCredits`（0 行 = 积分余额不够付本次预扣，**调用方据此拒绝请求**而不是抛异常 —— 拒绝是业务结果，不是故障，见 §10.6）。这是**全项目唯一一类允许的注解 SQL**：MyBatis-Plus 的 `LambdaUpdateWrapper` 做不了带参自运算（`setSql` 只能拼字符串，比注解更脏），而注解 SQL 仍属「零 Mapper XML」（红线 2 禁的是 XML）。新增同类条件写操作照此办理，不要偷偷引 XML。
  - 扣款成功后**同事务**写 `balance_transactions`（`change_amount` 消费记负数 + `balance_after` 快照），并用 `ref_type`/`ref_id` 指回业务单据（如 `subscription_order`）。
  - **发积分同理，入账与留痕必须同事务**：只加 `credit_accounts.balance` 不写 `credit_rewards` 批次，用户会看到「总积分涨了但奖励列表里没有这一笔」；只写批次不入账，则是有账无钱。
- **额度的数值必须入库，禁止从文案里解析**：套餐送多少积分要存在 `subscription_plans.monthly_credits`，**绝不许去正则抠 `subscription_plan_features.content` 里的 "2,000"** —— 那是给用户看的文案，运营随时改措辞，靠它发积分迟早发错（发放口径 = `monthly_credits × period_months`）。价格、周期时长同理都有专属列。⚠️ 当前「描述/权益文案」与「数值列」之间**没有强绑定**，改一个必须手动改另一个。
- **下单类接口的请求体禁止携带金额**：只传业务标识（如 `planCode` + `billingCode`），价格一律服务端查库。请求带价格 = 把定价权交给客户端，改个数字就能一分钱买旗舰版。套餐名 / 周期名 / 周期时长要作为**下单时快照**存进订单表，之后运营改价不影响历史订单可读性。
- **弃用的列要及时删掉，不许留「化石列」**（2026-09-17 实例：`users.credits`、`users.plan`）：某字段一旦有了权威源（积分 → `credit_accounts`，套餐 → `user_subscriptions`），原列就必须连同**实体字段、全部读写点、迁移脚本里拴在它上面的回填语句、`schema.sql`** 一并删除。留着看似无害，实则三害：① 迟早有人读错源——本次就是前端拿永远停在 `free` 的 `users.plan` 显示套餐名，买了标准版的用户界面上写着「体验版」；② 迁移脚本的回填语句拴在这列上，删列后新库首跑直接报错；③ 双源必然漂移（库中该行 `credits=0` 而账户余额 8000）。
  - **删列的正确姿势**：① 先把存量数据并入新权威源，**再**删列，两步在同一次迁移调用里；② 并入必须幂等（`WHERE NOT EXISTS (SELECT 1 FROM 新表 ...)`），且**合并失败就不删列**——宁可留个冗余列也不能丢数据；③ 删列本身用 `columnExists()` 判定后执行（`DbMigrationRunner#dropColumnIfExists`），列已不存在直接跳过；④ 删列迁移**必须排在目标表建表之后**（合并目标得先存在）。
  - 判断依据要落到数据上：删前查一次「仍有非默认值且无新权威源记录」的行数，为 0 才动手（本次 `SELECT COUNT(*) FROM users WHERE credits <> 0 AND NOT EXISTS(...)` = 0）。

### 10.4 「建表 + 初始数据」脚本范式

新增一张**需要初始数据**的业务表（如套餐、字典、渠道配置）时，整份 DDL + 种子数据写在一个 `db/migration_xxx.sql` 里，
由 `DbMigrationRunner#runScript()` 执行（内部 `EncodedResource` 显式 UTF-8 + `ScriptUtils`），**以「表是否存在」为总开关**：

```java
private void createXxxTables() {
    Integer count = jdbcTemplate.queryForObject(
            "SELECT COUNT(*) FROM information_schema.TABLES " +
                    "WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'xxx'", Integer.class);
    if (count != null && count > 0) { log.debug("xxx 已存在，跳过迁移"); return; }
    try (Connection conn = dataSource.getConnection()) {
        runScript(conn, "db/migration_xxx.sql");   // ← 不要直接调 ScriptUtils，见上方说明
    }
    log.info("迁移完成：xxx 表已创建并写入初始数据");
}
```

- 脚本内 `CREATE TABLE IF NOT EXISTS` + 种子数据用 `INSERT IGNORE`（配合唯一键），保证脚本可重复执行。
- **建表语句必须带 `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`**（两个都写，原因见 §10.3）。
- **中文 `COMMENT` / 种子数据只能靠 `runScript()`（UTF-8）写库**，否则一律变乱码，且不可逆。改完脚本用 `SHOW FULL COLUMNS FROM 表名` 抽查一条中文备注再收工。
- **总开关用「表是否存在」而不是「每次开机都 INSERT IGNORE」**：后者会在运营改过文案/价格后又把种子数据插回去。
  表已存在 = 数据已交付运营，后续改动走 SQL 或后台，不再由代码插手。
- 种子数据的 `SELECT` 子句里避免引用目标表本身；需要关联时用 `INSERT ... SELECT ... JOIN 主表`。
- **需要「按已存在用户回填」时**（如积分账户）：用 `INSERT INTO ... SELECT u.id, ... FROM users u WHERE NOT EXISTS (SELECT 1 FROM 目标表 t WHERE t.user_id = u.id AND ...)`，
  这样可重复执行且**不会覆盖运营改过的余额/状态**。实例见 `db/migration_credits.sql`。
  - 回填只覆盖存量数据；**新注册用户由 Service 懒初始化**（首次访问时判存在再插入，唯一键兜底并发），不要把回填逻辑放到注册流程里依赖。
- **尚无真实产生路径的数据（演示数据）**：脚本里必须用注释显式标注「演示数据」并写明真实逻辑落地后应清空，
  否则后人会把假数据当真实业务数据排查。时间字段建议用 `DATE_SUB(NOW(), INTERVAL n HOUR)` 相对偏移，避免种子数据随时间失效。

### 10.5 「只建表、不写种子数据」的表

有些表的记录**只能由真实业务动作产生**，塞种子数据等于伪造业务事实。现有四处，脚本统统**只建表、一行 INSERT 都没有**：

| 表 | 脚本 | 为什么不能造种子 |
|---|---|---|
| `user_subscriptions` | `db/migration_user_subscriptions.sql` | 「某用户买过旗舰版」只能由支付/开通流程写入 |
| `subscription_orders` | `db/migration_balance_orders.sql` | 订单是交易凭证，演示订单等于伪造交易 |
| `balance_transactions` | `db/migration_balance_orders.sql` | 流水要能和 `users.balance` 对账，假流水会把账做不平 |
| `subscription_credit_grants` | `db/migration_subscription_upgrade.sql` | 发放计划是「哪几期已交付」的凭据，假计划会真的发积分出去 |

（校验此类分支时临时插一行、验完即删，不留痕。）

配套约定：

- **「用户状态 → 界面默认值」的判断一律放服务端**。例：订阅弹框的默认选中项由 `SubscriptionService#getPlans` 推导 ——
  查 `status='active' AND expires_at > NOW()`：命中则选中**已购套餐的下一档**（这个弹框是「升级」入口，落点应是用户下一步要买的那档；
  已是最高档则选中自身，此时只能续费）；未命中（从未购买 / 已过期 / 已取消 / 已购套餐已下架）则回落到
  `subscription_plans.is_default` 的套餐与它自己的默认周期。计费周期优先沿用已购订阅的 `billing_code`
  （该 code 三档套餐通用），没有则用套餐自身的 `is_default`。
  - **「哪些档不可买」同样由服务端下发**：`locked` = 低于已购档一律 `true`；等于已购档时**仅当存在更高档**才 `true`
    （否则等于允许降级、或把同一档重复卖一次）；已是最高档则放开自身以便续费；从未购买则全 `false`。
    档位顺序就是 `sort_order` 升序（标准版 → 高级版 → 旗舰版），**不引额外的等级字段**，运营调顺序即调档位。
    ⚠️ 边界必须处理：最高档若把自己也锁掉，弹框会变成「全部置灰、无法支付」的死界面 —— 校验时务必覆盖这一档。
  - **前端只消费 `selected` / `defaultOption` / `locked` 标记，不参与判断**，改规则时两端不必同时发版。
- **过期不靠定时任务刷状态**：查询条件里直接比较 `expires_at > NOW()`，`status` 只用来表达「被主动取消/退款」。
  这样即使定时任务挂了、服务重启了，过期判定也不会错。
- **一次支付 = 一个事务里的八件事**（实例：`SubscriptionOrderService#payWithBalance`）：① 校验 → ② 折算 → ③ 原子扣余额 →
  ④ 写订单（原价 / 抵扣 / 实付三方留痕）→ ⑤ 写余额流水 → ⑥ 订阅行变更 + 预生成发放计划 → ⑦ 发放新周期当期积分 →
  ⑧ 回收旧套餐当月未消耗积分。任何一步失败全回滚，绝不能出现「钱扣了但订阅没开」「订阅开了钱没扣」「钱扣了订阅也开了、积分却没到账」。
  - **积分按月发放，不再一次发满**：一次订阅 = 覆盖总月数份「月度权益包」，每期一份积分。下单时**预生成整段计划**
    （表 `subscription_credit_grants`，年付 = 12 行，第 1 期立即发放、其余 `pending`），之后靠**惰性补发**
    （`CreditGrantService#grantDue`，挂在下单事务、登录取用户信息、积分总览、奖励列表等入口）补齐「已到点未发放」的期数。
    **不引定时任务**：零调度器、无单点、停机不丢；代价只是「用户长期不登录则不到账」，而他不登录也就不消耗，不构成损失。
  - **发放幂等靠两道锁**：先按唯一键 `uk_sub_period(subscription_id, period_index)` 插入去重，再用「`WHERE status='pending'` 条件更新抢占」
    防并发重复入账（0 行即已被别的请求发过）。补发与入账必须**整体同事务**，否则会留下「标记已发但账户没到账」的永久缺口。
  - **为什么改按月发**：未来月份积分若已躺在用户账户里，「退未生效月的钱」就等于用户既拿退款又留积分（双重补偿）。
    按月发放后，退款口径从「防套利的保守阀」变成「按交付事实如实结算」，升级时也不必回收未来月积分 —— 把剩余 `pending`
    计划整体置 `cancelled` 即可（这正是本方案比「一次发满」简单的地方）。
  - **续费不立即发积分**：续费是往后顺延，要等新周期开始才发，否则用户会在重叠期拿到两份；发放计划从「原有期数 + 1」起追加。
  - 积分发放失败必须**抛异常让整笔支付回滚**（`addBalance` 返回 0 行时），不能吞掉 —— 宁可让用户重试支付，也不能扣了钱不发积分。
  - **回报给用户的「本期到账积分」必须查实际状态，不许凭「计划已建」假设已到账**：发放可能因任何原因没落地，
    报一个根本没进账户的数字比不报更糟（`granted` 取第 1 期计划的真实 `status`）。
- **升级 = 替换，不是叠加**（`SubscriptionUpgradeService`）：旧订阅立即置 `upgraded`、记录 `ended_at` 与 `upgraded_to_plan_code`、
  取消剩余发放计划；新订阅从升级日起算。这样**同一用户任何时刻最多只有一条 active 订阅** —— 这条不变量是所有抵扣计算的前提
  （否则「旧套餐剩余价值」根本无从定义）。不用「并行叠加」是因为那样用户会为重叠时长付两份钱、积分也发两份，旧行还会变成任何界面都不显示的孤儿。
  - **折算模型：一次订阅 = n 份月度权益包** —— `n` = 覆盖总月数、`P` = 净支付额 `net_paid_amount`、`m = P/n`（月均价）、
    `i` = 当前期号、`F = n − i`（未生效整月数）、`t` = 当月剩余时间比例、`u` = 当月批次 `remaining / total`、`k = min(t, u)`；
    **抵扣 `G = m × F + m × k`**，**应付 `A = max(新套餐价 − G, 0)`**。三段结算：已过完的月份**不退**（权益已完整交付，
    否则用满 11 个月再升级还要退钱）、当月按 `m × k` 退、未生效月份全额退 `m × F`。
  - **当月取 `min(t, u)` 而不是只看积分**：只看积分的话，「9 月 1 日买月付、9 月 28 日升级、期间没怎么用 AI」会算出全额抵扣 → 用户白用 28 天；
    反过来只看时间，则积分已耗尽还能退钱。两个维度**取小**，两侧归零条件都成立（积分耗尽 → 0，时间走完 → 0）。
  - **基数用净支付额，不用套餐标价**：标价作基数可被反复套利（拿按标价算出的剩余价值去抵新价 = 平台额外补贴）。
    关键性质是**无套利**：刚买当天升级（`k = 1`）时累计支出恰好等于直接买新套餐的价格，之后每一元超出都精确对应他真实消耗掉的旧权益。
  - **回收积分的比例必须与折钱完全相同（同一个 `k`）**：钱按 `k` 退了当月，积分就按 `k` 收当月
    （`CreditRewardMapper#reclaim` 扣批次 + 账户扣减 + 负向流水，三者同事务，见 `CreditService#reclaimSubscriptionCredits`）。
    若改成「未用完的全收走」，会出现「退 43% 的钱、却收走 80% 的积分」，还会推出「越早升级越亏积分」的反直觉结论。
  - **抵扣额截断到不超过新套餐价，超出部分作废**（不结转、不退现）；产生作废时**下单必须带 `confirmWasted=true` 凭据**，否则拒绝服务 ——
    服务端不采信 UI 拦截，这是防「绕过界面直调接口被静默截断」的凭据。
  - **金额恒等式必须断言**：`amount = original_amount − discount_amount`，不成立即抛异常回滚整笔（落库后再自检一次）。
  - **折算算法只有一处实现**：同一份 `Quote` 同时供只读预览 `GET /subscription/preview` 与下单事务使用；
    前端算的只是展示，下单仍由服务端用**库表价格**重算，客户端传金额一律不采信。
  - **降级硬拦在服务端**：已购低档订阅仍在生效时不允许再买更低档（`sort_order` 比较），UI 置灰只是体验，服务端必须自己再拦一次。
  - **续费要顺延，不能从今天重算**：同套餐仍在有效期内再次购买，到期时间在原 `expires_at` 上 `plusMonths(periodMonths)`，
    否则用户续费会白扔剩余天数。此时**更新原行**而不新增，保证「一个套餐最多一条 active」；每次购买的完整历史留在订单表里。
  - **周期时长取 `subscription_plan_billings.period_months`，不要拿 `unit` 的 `/月` `/年` 文案做判断**（文案随时会改，
    且未来有季付/半年付时文案也表达不了）。该列由迁移补 + 按 `code LIKE 'yearly%'` 回填，不依赖 Java 常量表。
  - 到期时间只在**服务端**算，并随下单结果返回（`expiresAt`）；前端那个「有效期至」只是按 `periodMonths` 的粗略预览，
    续费顺延时前端根本算不出来。

### 10.6 聊天积分扣费：两阶段（预扣 → 结算 → 退款）

对话消耗积分**不做「跑完再扣」** —— 余额为 0 的用户也能跑完一次昂贵任务，扣费时扣不动，平台白送成本。
统一走 `ChatBillingService` 的三段式，做任何涉及对话扣费的改动前必须先读这一节：

| 阶段 | 入口 | 做什么 | 失败/拒绝的样子 |
|---|---|---|---|
| ① 预扣 | `hold(userId, requestId, conversationId, channel, modelCode, estInputTokens)` | 按「待发文本 chars/4 估输入 + `model_pricing.max_output` 估输出」算预扣额，**条件扣减真金**（`deductCredits`），落 `credit_holds` 单 | 余额不够 → 返 `HoldResult.insufficient`，**不建单、不落用户消息、零副作用** |
| ② 结算 | `settle(...)` 在 `done` 处 | 抢占预扣单（`held→settled` 条件更新）→ 按真实 usage 重算 → **多退少补** → 写 consume 流水（`message_id` 唯一索引双保险）→ 按「先到期先扣」扣减展示批次 | 抢占 0 行 = 已被结算/退款，直接跳过（幂等） |
| ③ 退款 | `refund(...)` / `sweepExpiredHolds(...)` | 零产出、上游报错、启动失败 → 全额退；`held` 超 10 分钟 → 惰性清扫退款 | 退款失败只 WARN，下一轮清扫再试 |

铁律：

- **计价数据一律查库**（红线 14）：模型单价在 `model_pricing`（含 `cache_ratio` 缓存折率、`is_free`、`is_fallback` 兜底行），
  分组倍率在 `credit_group_ratio`（`plan:<code>` → `channel:<通道>` → `default` 三层查找，按订阅档位 / 通道分别配倍率）。
  连「未登记模型的兜底单价」也在表里，**代码里不许出现任何单价数字**。
- **预扣额按上限估是刻意的**：真跑满才花得完，正常对话结算时都会退一笔。多算会退、少算会补，所以粗估不影响最终账，
  只影响「能不能发起这次请求」的门槛。
- **金额恒等式 `cost + refunded == preConsumed` 必须成立**，它由「先抢占再算差额」保证；
  补扣允许余额瞬时为负（`addBalance` 传负数），下一轮预扣自然拦下。
- **积分金额一律两位小数（`DECIMAL(12,2)` + `BigDecimal`），一次真实调用下限 0.01 积分**（2026-09-21 精度改造）：
  `computeCost` 返回 `BigDecimal`，内部按 8 位算、落账前 `HALF_UP` 归到 2 位；`preConsumed / refunded / estimatedCost`
  全链路同为 `BigDecimal`。**禁止再写 `max(1, ceil(raw))` 这类整数计费** —— 以 pro 价（输入 0.2 积分/千 token）算，
  1 积分 ≈ 5,000 输入 token，而一句「你好」真实成本约 0.001 积分，整数向上取整会把小额请求放大三个数量级
  （用户实测「消耗积分怎么都是整数」即为该口径的直接结果）。
  ⚠️ 配套：列类型必须同步加宽（`DbMigrationRunner#widenCreditsColumns` 幂等把历史 INT 列改成 `DECIMAL(12,2)`）——
  Java 侧算出 0.01 而列还是 INT 时会被**静默取整成 0**，账看着扣了、余额没动，比整数计费更难查。
  新增任何积分列都按两位小数的 `DECIMAL(12,2)` 建，不要再出现 INT 积分列。
- **一切金额都由服务端算好回传**：`done` 事件带 `credits{cost, preConsumed, refunded, balanceAfter, estimated}`；
  消息表 `messages.credits_cost / credits_estimated` 冗余一份结算快照，历史重载时前端直接读。**前端不许自己按 tokens 乘单价**。
- **不引定时任务**：僵尸预扣单清扫挂在发消息、登录取用户信息、积分总览等必经入口（同 `CreditGrantService#grantDue` 的惰性思路），
  超过 10 分钟（远大于一次对话的生命周期）的 `held` 单批量退款。
- **全通道同一套引擎、不同入口**：Web 聊天在 `ChatController` 三处接入（预扣 / done 结算 / `doFinally` 兜底）；
  办公助理（iLink）在 `ChannelReplyService` 两处接入（预扣 / 结算），`credit_holds.channel` 区分（`web` / `ilink`），倍率可差异化。
  ⚠️ iLink 侧 `requestId` 用「账号 id + 消息 id」派生，保证消息重推不二次预扣。
- **余额不足的错误码是 `NO_CREDITS`**：SSE `error` 事件带 `{"code":"NO_CREDITS","message":"...需要 N 积分，当前可用 M 积分..."}`，
  前端据此出「购买/升级」横幅而不是报错；iLink 通道则回一条微信文本提示。文案必须带「应需 / 现有」两个数字。
- **流水标题 = 本轮用户提问，不是会话标题**：会话标题只由首条消息生成，一个会话问上三轮时后续流水全挂着第一句话
  （明细页看着像重复行）。Web 聊天在 `ChatController#recordTitleOf(content)` 取本轮内容，办公助理取当轮消息并加「办公助理·」前缀；
  折叠空白 / 截断 32 字 / 空值兜底统一由 `ChatBillingService#titleOf` 负责，各入口不要各写一套。
- **估算口径走 `credit_transactions.estimated` 列（红线 17）**：标题只写「这是哪一轮提问」，
  绝不再拼 `[估算] ` 前缀。明细页的「约」由该列驱动。

涉及的表与列：新建 `model_pricing` / `credit_holds` / `credit_group_ratio`（`db/migration_chat_billing.sql`；前两张带种子、`credit_holds` 只建表；
`credit_holds.estimated_cost / actual_cost` 为 `DECIMAL(12,2)`）；
`credit_transactions` 扩 `message_id(uk) / hold_id / input_tokens / output_tokens / estimated`；`messages`、`channel_messages` 扩 `credits_cost / credits_estimated`（`credits_cost` 为 `DECIMAL(12,2)`）。
扩列、唯一索引、精度加宽（`widenCreditsColumns`）与「剥离历史标题 `[估算]` 前缀 + 按当轮提问重写」的回填都在 `DbMigrationRunner#chatBillingTables` 里逐列 ALTER。

改动后的验证基线（都在工作区根，凭据从 `application-local.yml` 读取、不写死）：
- `verify_billing.py`：对着真库 + 真后端跑 57 项断言 —— 迁移落表 / 预扣→结算闭环恒等式 / 余额不足零副作用 / 僵尸单清扫 / 免费模型零成本 / iLink 通道 / 抢占互斥。
- `verify_billing_title.py`：两轮真实问答 —— 流水标题 = 各轮提问（互不重复、无 `[估算]` 前缀）、`estimated` 落库为 0、usage 是真实值（不等于 `chars/4` 兜底公式）、历史污染行已回填。

## 12. Agent / Tool 扩展规范

### 12.1 新增一个工具

工具类**必须同时实现 `Tool` 接口 + 标注 Spring AI `@Tool` 注解**，`ToolRegistry` 用一个 `List<Tool>` 收集全部。

```java
@Slf4j
@Component
public class MyTool implements Tool {

    @Override public String name() { return "MyTool"; }
    @Override public String description() { return "Use when ... (英文，LLM 依据此描述决定是否调用)"; }
    @Override public Permission requiredPermission() { return Permission.ASK_USER; }
    @Override public boolean isReadOnly() { return true; }

    @Override
    public Map<String, Object> parameterSchema() {
        // JSON Schema
        Map<String, Object> props = new HashMap<>();
        props.put("path", Map.of("type", "string", "description", "..."));
        return Map.of("type", "object", "properties", props, "required", List.of("path"));
    }

    @org.springframework.ai.tool.annotation.Tool(name = "MyTool", description = "...")
    public String execute(
            @ToolParam(description = "...") String path) {
        // 实际实现
    }

    @Override
    public ToolResult execute(ToolContext ctx, Map<String, Object> args) {
        long start = System.currentTimeMillis();
        String out = execute((String) args.get("path"));
        return ToolResult.ok(out, (int) (System.currentTimeMillis() - start));
    }
}
```

要点：

- `name()` 与 `@Tool(name=...)` **必须一致**。
- `description()` 与 `@Tool(description=...)` **必须一致**（前者给旧链路，后者给 Spring AI）。
- **`description()` 用英文写**，是给 LLM 看的，要写清"什么时候用我"。
- `parameterSchema()` 与 `@ToolParam` 描述**必须一致**。
- 必须返回 `ToolResult`，**禁止抛异常穿透**（失败用 `ToolResult.fail(msg, ms)`）。
- `isReadOnly() = true` 的工具可被并行执行，判定标准是"无副作用"。
- 工具里**不要自己弹框问用户**，需要交互时用 `AskUserQuestionTool`。

### 12.2 权限档位

`Tool.Permission` 三档与数据库 `permissions` 表对应：

| 枚举 | 语义 | 数据库 `default_mode` |
|---|---|---|
| `AUTO_ALLOW` | 直接执行，不问 | `auto_allow` |
| `ASK_USER` | 按用户全局模式决定（`manual` 弹框 / `smart` 自动批准 / `fully` 全放行） | `ask_user` |
| `DENY` | 永远拒绝 | `deny` |

新增工具**必须**在 `db/schema.sql` 的 `permissions` 初始化 `INSERT` 语句里追加一行（当前 15 个工具，与 `tool/` 下的实现一一对应）：

```sql
INSERT INTO permissions (tool_name, default_mode) VALUES
  ('Read',         'auto_allow'),
  ('Write',        'ask_user'),
  ('Delete',       'ask_user'),
  ('Shell',        'ask_user'),
  ...
```

判定原则：**只读、无副作用 → `auto_allow`**；**有写入/执行/外发 → `ask_user`**。`deny` 目前没有内置工具使用。

### 12.3 Tool 上下文

```java
record ToolContext(Long sessionId, Map<String, Object> metadata) {}
```

工具执行需要用户身份时，从 `UserContext.get()` 取（ThreadLocal）。

需要**本次运行绑定的工作空间**时，从 `AgentContext.getWorkspaceId()` 取（同为 ThreadLocal，在同一个 agent 线程入口设置）。
两者**刻意分开**：`userId` 是请求身份（任何 HTTP 线程都有），工作空间是**本次 Agent 运行**的上下文，
而且必须是 `AgentEngine` 解析后的值（跨设备 / 已移除的空间在那里已经变成 null）。

⚠️ 线程陷阱：`AgentEngine#run` 把 agent 循环跑在 `new Thread(...)` 里，ThreadLocal 不跨线程 ——
`UserContext.set` / `AgentContext.setWorkspaceId` 都必须在**那个线程的入口**调用，并在 `finally` 里 `clear`。
漏了 set 不报错，工具里读到就是 null（表现为「对话里创建的任务永远没有空间」，很难查）。

#### 12.3.1 自动化任务与空间（2026-09-21 追加）

- 落库列 `schedules.workspace_id`，类型必须 `BIGINT UNSIGNED NULL` —— 与 `sessions.workspace_id` 同型；
  类型不一致会让关联比较走隐式转换、索引失效。
- 两条写入路径：① 页面「手动新建」→ 客户端先建/复用同名空间，`POST /schedules` 带 `workspaceId`；
  ② 对话中创建 → `ScheduleTool` 从 `AgentContext` 取当前会话的空间**自动**带上。
  ⚠️ **不要**把 `workspaceId` 做成工具参数指望模型填 —— 模型根本不知道空间 id。
- **运行时必须把空间继承到会话上**（否则任务「会说不会做」）：
  `ScheduleRunner` 用 `workspaceService.find(userId, workspaceId)`（宽松取、不抛异常）拿实体 →
  用它的 `deviceId` 建会话 → 把同一个 `deviceId` 写进 `ChatMessageRequest`。
  漏掉 `deviceId` 时 `AgentEngine` 会判成「跨设备」，会话退回无空间，8 个本地类工具整体不下发。
- 绑定的空间已被移除 → 记 WARN 后按无空间继续执行，**不要把任务标记为失败**。
- 🔴 **空间的生命周期**（2026-09-21）：服务端**唯一**会自动删除空间登记的入口是**会话删除**
  （`SessionService#delete` → `removeWorkspaceIfOrphaned`），判据两条同时成立才删：
  ① 该空间下**已无任何会话**（含已归档 / 置顶 —— 行还在就可能被恢复，不能只看 `status='active'`）；
  ② **没有被任何自动化任务引用**（`schedules.workspace_id`）。第 ② 条例外必须守住：任务的空间是它的
  执行目录，删了它下次触发就取不到空间、悄悄退回「无空间执行」—— 正是 §8.5 要避免的那种静默降级。
  前端配套：删会话成功后若该会话绑过空间 → `workspaceStore.load(true)` 强刷列表（前端规范 §9.4）。
  ⚠️ 只删元数据行，**磁盘目录一律不动**（与 `WorkspaceService#delete` 同口径）
- 任务的执行设备由**空间自身**决定，与「在哪台机器上点的创建」无关；`ScheduleService.create`
  只校验空间属于该用户（`getOrThrow`，越权 404），**不**校验设备。

### 12.5 工具执行通道：本地类工具下沉客户端

产品部署在云服务器上，但**工作目录在用户本机** —— 服务端拿到的相对路径落在 JVM 工作目录、绝对路径在服务器上根本不存在
（更糟的是同形路径会静默读写无关目录）。所以文件/命令类工具的执行者不是服务端，而是**客户端 Electron 主进程**：

```
客户端                                        云端
  │  POST /api/chat/stream ──────────────────▶ Agent 循环（调模型 / 解析 tool-call）
  │  ◀──── SSE 事件 tool_call ────────────────┤ ① 按 ToolRouter 判归属
  │ ② 本机执行（沙箱内）                        │
  │  POST /api/chat/tool-result/{callId} ────▶ ③ CountDownLatch 解锁
  │  ◀──── SSE delta / done ──────────────────┘ ④ 结果喂回模型，继续循环
```

**通道不必新造协议** —— 它复用本项目已有的「服务端请求 → 客户端回传 → 解锁」范式（工具审批 `POST /chat/permission/{requestId}`、
反问 `POST /chat/question/{requestId}` 都是这个做法），不引 WebSocket：

- `ToolRouter.isClientTool(name)` 是**归属判定的唯一出处**（Read / Write / Edit / Delete / Glob / Grep / Shell / Exec 为本地类）。
  新增工具时必须想清楚它归哪一边，别在 `AgentEngine` 里散着判断。
- `ClientToolGateway` 持有 `pendingToolCalls`（`callId → CountDownLatch`），**超时必设**（默认 120s，Shell/Exec 可放宽到 600s），
  超时即按失败回喂模型 —— 否则模型调用一次、服务端线程就永久挂一个。
- 上行 `resolve` 必须校验 **`callId` 归属当前用户**，取不到/已超时/非本人一律返回 404，**不能抛 500**（客户端不需要重试）。
- SSE 出流被取消/断线时必须**清空该用户所有在途调用**（`releasePendingToolCalls` 挂在 `doFinally`），否则线程泄漏。
- ⚠️ **服务端同名 Java 工具保留但必须下掉挂载**：否则同一个工具名会被服务端和客户端各执行一遍。
- **无空间会话不下发本地类工具**：没有工作空间 = 没有可操作目录，下发只会让模型反复调用失败（`resolveToolCallbacks` 负责剔除）。

### 12.6 路径沙箱收口在客户端（`resolveInRoot`）

**沙箱判定只能写一处**。本项目有 8 个路径入口（6 个文件工具 + Shell/Exec 的 cwd），各自判断必然漏一个 ——
一律走客户端主进程的 `workspacePaths.resolveInRoot(root, input)`：

- 相对路径以**空间根**为基准（不是 JVM 工作目录、不是用户主目录）；
- 绝对路径**先 `toRealPath()` 解符号链接，再判前缀**。只比字符串会被 symlink 绕过（根内建一个指向 `/etc` 的软链即可越界）；
- 拒绝 `..` 上跳、UNC 网络路径、以及系统关键目录；
- 目标不存在时要按「父目录 realpath 再拼接」判定（否则 Edit/Write 新建文件必失败）。

⚠️ 服务端**不做**路径判断，也**不该**做：它没有路径。服务端保留的是**策略层**（哪些工具可用、权限档位、配额）。

### 12.7 配额类业务数值必须落 `subscription_plan_quotas`

**`subscription_plan_features` 是展示文案表**（`icon` + 「支持 N 个工作空间」这类中文句子），**不能拿来做判断** ——
解析自然语言等于把运营文案当 API（红线 14）。凡「按套餐档位限制的数量」一律进
`subscription_plan_quotas(plan_code, quota_key, quota_value)`，`quota_value = -1` 表示不限：

| 键 | 用途 |
|---|---|
| `workspace_limit` | 工作空间数量上限（free 3 / standard 5 / premium 20 / flagship 99） |
| （预留） | 自动任务个数等后续配额直接复用同一张表 |

规则：

- **`free` 行 = 未订阅时的默认档**，与 `SubscriptionService#currentActivePlan` 返回 null 的语义对应；查不到额度时按 **0（最紧）** 兜底并 WARN 提醒运营漏配。
- 额度读取一律走 `WorkspaceQuotaService`（或同类服务），**禁止在 Service 里写死档位常量、也禁止前端自行推算档位**。
- **降级只冻结新增，绝不删除既有数据**：订阅过期导致「已用 > 上限」时，既有空间必须留着（它们代表用户磁盘上真实存在的目录）。
- 额度是**账号级**（跨设备合计），不是设备级。

## 13. SSE 流式事件契约（前后端强耦合，改动需双方同步）

聊天接口：`POST /api/chat/stream`，`produces = text/event-stream`。

| event | data | 说明 |
|---|---|---|
| `reasoning` | `{"text": "..."}` | 深度思考增量 |
| `text` | `{"text": "..."}` | 正文增量 |
| `tool_call_start` | 工具名 + 入参 | 工具开始执行 |
| `tool_call_end` | 工具名 + 结果 + 耗时 | 工具执行结束 |
| `tool_call` | `{callId, name, args, workspaceId, deadlineMs, permissionMode}` | **本地类工具**下发客户端执行（见 §12.5）。**载荷不含任何路径**（红线 18），客户端用 `workspaceId` 在本地查路径 |
| `tool_cancel` | `{callId}` | 终止客户端正在执行的工具；取消 / 断线时下发，客户端据此杀子进程 |
| `permission_request` | 工具名 + 入参 | 需要用户授权，前端弹框 |
| `tool_blocked` | 工具名 + 原因 | 被权限策略拒绝 |
| `question` | 问题 + 选项 | Agent 反问用户 |
| `compress_start` / `compress_end` | — | 上下文压缩边界 |
| `error` | `{"code": "...", "message": "..."}` | 错误。`code=NO_CREDITS` 表示积分不足被预扣拦下（`message` 带「需要 N 积分 / 当前可用 M 积分」） |
| `done` | `{"finalContent": "...", "usage": {...}, "credits": {...}}` | 结束，携带完整回复、用量与本次结算结果 |

规则：

- `tool_call`（本地执行）与 `tool_call_start/end`（服务端执行）是**两条不同的链路**，别混：前者是「请求客户端去干」，
  模型还没拿到结果；后者是服务端已经跑完了。改任一侧都要同步客户端 `toolChannel`（见 §12.5）。
- `done` 事件的 `finalContent` 是**落库依据**，由 `ChatController` 写入 `messages` 表。
- `done.usage` 为 `{"input_tokens", "output_tokens", "cache_hit_tokens", "cache_miss_tokens", "estimated"}`。
  `input/output` 取自 Spring AI 的类型化 usage（红线 16）；`estimated=true` 表示上游整段没给 usage、退化成 `chars/4` 估算，
  **正常链路不该出现 `estimated=true`**，出现了就是解析坏了。
  `cache_hit_tokens` 恒为 0：Spring AI 的流式聚合会把 DeepSeek 的 `prompt_tokens_details.cachedTokens` 丢掉
  （`UsageCalculator` 重建 `DefaultUsage` 时 `nativeUsage` 传 null），拿不到就按「全部未命中」保守计 ——
  这是**缓存拆分缺失**，与 `estimated`（token 是估算值）是两件事，别混。原生 flash 通道（自己读 SSE）能拿到真实拆分，两条通道口径在此处不一致。
- `done.credits` 由服务端两阶段结算产出：`{"cost", "preConsumed", "refunded", "balanceAfter", "estimated"}`，
  恒有 `cost + refunded == preConsumed`。为 `null` / 缺失 = 免费模型或未触发扣费，见 §10.6。
  **前端只消费这些数字，不许自己按 tokens 乘单价**；`balanceAfter` 回写 authStore 余额。
- **新增事件类型必须同步前端**（`api/session.ts` 的 `StreamCallbacks`），否则前端会静默忽略。
- **改动已有事件的 data 结构属于破坏性变更**，必须同版本发布前后端。
- 每个 event 都必须能被前端安全忽略 —— 即前端遇到未知 event 不能崩。

## 14. 日志规范

用 `@Slf4j` + 占位符（**禁止字符串拼接**）：

```java
// ✅
log.info("创建会话: userId={}, sessionId={}", userId, sessionId);
log.warn("Business error: code={}, msg={}", ex.getCode(), ex.getMessage());
log.error("Unexpected error", ex);   // 异常对象放最后一个参数

// ❌
log.info("创建会话: userId=" + userId);
```

| 级别 | 用途 |
|---|---|
| `error` | 需要人工介入的异常，**必须带堆栈** |
| `warn` | 业务异常、降级、可恢复失败 |
| `info` | 关键状态变更（登录、创建会话、迁移完成、工具注册） |
| `debug` | 排查用细节（跳过的迁移、参数内容） |

**禁止**：

- 打印密码、Token、API Key、完整请求体。
- 在循环里打 `info`（性能与磁盘）。
- 把大文件内容、完整 LLM prompt/response 打进 `info`。

配置现状：`com.lumenai.backend` = DEBUG，`org.springframework.ai` = DEBUG；日志文件 `logs/lumen-ai.log`，单文件 100MB、保留 30 天、总量上限 3GB。

⚠️ Boot 4 的滚动策略配置路径是 `logging.logback.rollingpolicy.*`（**不是** `logging.file.*`）。

**真实范例**（参考 `8d2e821`）：

```
perf(work-assistant): 绑定状态查询改为纯 DB 读取，删除 iLink 长轮询探测

- GET /work-assistant/accounts/{channel} 不再调用 probeSession。iLink 的
  getupdates 是长轮询，token 有效时服务端会挂住连接，探测必然要等满 8 秒
  读超时才返回，导致每次进入办公助理都卡 8 秒。
- 更严重的隐患：getupdates 的游标 get_updates_buf 由 Electron 主进程独占，
  服务端拿同一个 bot_token 再发一次空游标请求，可能把消息抢到探测请求上，
  造成桌面端漏收消息。
```

### 16.2 Windows 环境必须走 `-F` 文件

本机 `[Console]::OutputEncoding` 是 GBK，`git commit -m "中文"` 会把参数按 GBK 编码传给 git，**提交信息真会坏**（不是显示问题）。

```powershell
$enc = New-Object System.Text.UTF8Encoding $false
[System.IO.File]::WriteAllText("$ws\_msg.txt", $content, $enc)
git commit -F "$ws\_msg.txt"
```

git **输出**的中文乱码只是控制台解码问题，仓库里是合法 UTF-8。

### 16.3 常见 git 坑

- 中文文件名会被转义成 `\346\234\215...`，必须加 `-c core.quotepath=false`。
- **提交后必须回读** `git log --oneline`、`git ls-tree -r <sha>` 确认真实内容，不要相信 push 回显。
- 环境存在"自动暂存"行为：指定文件提交后，`.idea/vcs.xml` 等可能被顺带暂存成 `A`，提交完 `git restore --staged` 复核。
- **彻底移除已推送的敏感文件必须重写历史**（`git rm --cached` → `commit --amend` → `push --force-with-lease`），普通提交只是删工作区副本，历史里仍在。

```
.idea/workspace.xml  .idea/vcs.xml  *.iml     .codeartsdoer/
```
